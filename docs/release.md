# 版本号与发版规范

做法参照 Firefox Nightly / Rust nightly。本项目是 Node / Vite 前端项目。

## 版本号存在哪里

- 只存一处：`package.json` 的 `version`。当前值 `0.1.0`。
- 当前版本号还没有开发标记。**下一次发版后开始带开发标记**（例如发 `0.1.0` 后推进到 `0.1.1-dev`）。
- 构建命令：`npm run build`，产物在 `dist/`。

| 语言 / 构建 | 版本号存哪里 | 开发版写法 | 带哈希的写法 | 注意 |
|---|---|---|---|---|
| Node / Vite | `package.json` 的 `version` | `0.1.1-dev` | 构建时注入 `0.1.1-dev-<短哈希>` | 推进用 `npm version 0.1.1-dev --no-git-tag-version`；`npm version <正式版>` 会自己提交打标签，二选一，别重复打 |

## 通用规则

1. **平时版本号带开发标记。** 两次发版之间，`package.json` 里的版本号一直带 `-dev`。不带标记的版本号，一定是发出去的包。
2. **能取到 git 信息时，开发版接短哈希。** 例如 `0.1.1-dev-1a2b3c4`；工作区有未提交改动时再加 `+`。
3. **开发版不打标签，不建 Release。**
4. **版本号只存一处。** 其他地方（页面上的版本显示、产物文件名）在构建时从 `package.json` 读，不手抄。
5. **发版步骤：**
   1. 去掉开发标记（`0.1.1-dev` → `0.1.1`）。
   2. `CHANGELOG.md` 顶上加 `## <版本> · <日期> · <渠道>`，渠道是 `alpha` / `beta` / `rc` / `stable`。
      更新日志手写，面向用户，一行一条。先按上个标签以来的 `git log` 起草，给用户看过再定稿。
   3. 提交 `chore(release): <版本>`，打注释标签 `v<版本>`，推送分支和标签。
   4. **标签推出去后，马上再做一个提交，把版本号推到下一个开发版，并推送。**
      默认补丁号加一（`0.1.1` → `0.1.2-dev`）；预发布串把最后一个数字加一（`0.1.0-alpha.2` → `0.1.0-alpha.3-dev`）。
      用户说了要升次版本号或主版本号，才按用户说的改。提交信息 `chore(release): 开始 <下一个版本>`，不打标签。
   5. 日常 push 不改版本号。只有发版标签推出去后才推进。
6. **门禁**（发版脚本或 CI 第一步检查，任一不过就停）：带开发标记的拒绝；版本号与标签一致；
   标签在主分支上（`git merge-base --is-ancestor <tag> origin/main`）；已跟踪的文件没有未提交改动（`git status --porcelain --untracked-files=no` 为空）。
7. **发出去就不改。** 已推送的标签不移动、不重打；已发布的 Release 不改回草稿。发错了就发下一个版本。
8. **打发版标签并推送前，先问用户。** 用户同意后，第 5.4 步的推进提交和推送一起做，不再问。
